# v0.7 浏览器手动验证(给作者本人看的版本)

## 这是干什么的

我们把 DayRail 的同步层从 v0.6 的 SQLite + JSON 换成了 v0.7 的 Yjs CRDT + .dryj 二进制。代码改动巨大,7 轮独立 review 里**每轮都还能找出 HIGH 级 bug**。typecheck 全过、单元测试 93 个全过,但有些 bug 只能在**真实浏览器里跑真实流程**才能暴露。

下面这些场景每一个都对应 review 抓出过的真 bug。**至少跑完 1、2、3、4、5 这五个**(都不超过 5 分钟),其它的 6-10 是加分项。

跑的时候打开 Chrome DevTools(F12)→ Console 标签,后面有些步骤要在里面输命令查值。

## 准备工作

最方便的做法:**用同一台 Mac 上的两个不同 Chrome profile** 模拟"两台设备"。

- 打开 Chrome → 右上角头像 → 添加 → 创建一个叫 "DayRail-A" 的新 profile。
- 同样再创建 "DayRail-B"。
- 两个 profile 都登录**同一个** Google 账号(用来同步 Drive)。
- 两个 profile 都打开 `http://localhost:5173`(假设用 `pnpm --filter @dayrail/web dev` 跑起来的)。

下面提到 **A** 和 **B** 都是这两个 profile。

## 场景 1:验证 v0.7 没有破坏数据合并(最重要)

**为什么测**:整个 v0.7 的核心承诺就一句话——「两台设备改同一个东西不再冲突,自动合并」。这是用户原话提出来的痛点,也是整个迁移的目的。如果这个不工作,前面所有改动都白做。

**怎么测**:

1. **A** 和 **B** 都启动并连接 Drive。两边显示一致的数据。
2. 在 **A** 上:**断网**(Mac 关掉 Wi-Fi)。新建一个任务叫「测合并 X」,标题就用这个文字。
3. 在 **B** 上:**保持联网**。打开同一个 task list 视图(可能要刷新一下从 Drive 拉到最新)。新建另一个任务叫「测合并 Y」。
4. 等大约 70 秒(让 B 的 60 秒 debounce 自动 push 到 Drive,完整跑完一次)。
5. **A 联网**(打开 Wi-Fi)。等 30 秒。

**通过 ✅**:A 和 B 最后都能看到「测合并 X」和「测合并 Y」两个任务。两边都没丢东西。

**失败 ❌**:任何一边只看到自己的那个任务。

## 场景 2:验证「同时点完成」不再冲突

**为什么测**:用户原话是「我在 A 上把任务标完成了,回到 B 看到还是没标,又点了一次完成」——v0.6 这种场景会弹冲突卡片让你二选一,v0.7 应该自动合并。

**怎么测**:

1. **A** 和 **B** 都连了 Drive,两边都看得到同一个任务,状态是「未完成」。
2. **A** 断网。点该任务的「标记完成」。
3. **B** 断网。点同一个任务的「标记完成」。
4. **A** 和 **B** 都联网。等 70 秒。

**通过 ✅**:两边任务都是「已完成」,**没有任何弹窗**问你要保留哪边。

**失败 ❌**:出现冲突弹窗(说明 v0.7 的 conflict UI 没删干净);或者一边状态变回去了。

## 场景 3:验证「立即同步」按钮关 tab 不丢数据

**为什么测**:Round 5 抓的 bug——你点了「立即同步」,系统说「拉完了」,但你的本地修改其实还没传上去,如果你立刻关 tab 就丢了。Round 6 修了。

**怎么测**:

1. **A** 和 **B** 都连 Drive,内容一致。
2. **B** 上做几个任意修改(改任务标题、加 task 之类)。**别等 60 秒**。
3. 在 **B** 上:Settings → 同步 → 点「**立即同步**」按钮。
4. 按钮下方应该显示「**已合并云端改动并推送**」(注意是「**并推送**」)。
5. **立刻关掉 B 的 tab**(在 5 秒内)。
6. 重新打开 B 的 tab。

**通过 ✅**:你刚才在 B 上做的修改还在。**A 上手动刷新或等 5 分钟周期 probe 后,A 也看到了**。

**失败 ❌**:
- 步骤 4 的提示只说「已合并云端改动」,**没**「并推送」三个字 → round 6 修的 return 值没生效。
- 或者重开 B 后修改丢了 → round 5 的根本 bug 回归。

## 场景 4:验证「迁移已有 v0.6 数据」不会被覆盖(超级重要)

**为什么测**:Round 6 抓的 **CRITICAL** bug——如果你按 ERD 写的迁移流程跑(导出 v0.6 → 跑迁移脚本 → 在 v0.7 里 Settings 导入 → 连 Drive),round 5 的代码会**静默删掉你的迁移数据**。Round 6 修了,但需要验证修对了。

**这步只有当你真的有 v0.6 数据的时候做。** 没有的话跳过。

**怎么测**:

1. 在你**还没升 v0.7** 的 v0.6 浏览器里,Settings → 高级 → **下载 JSON**,文件存桌面。
2. 升级到 v0.7(本地切到这个分支)。
3. **在终端**:
   ```
   cd dayrail/tools/migrate
   pnpm migrate ~/Desktop/dayrail-backup-XXX.json
   ```
   会在桌面同位置生成 `dayrail-backup-XXX.dryj` 文件。
4. 启动 v0.7 的 dev server。在浏览器里**重置一次本地数据**:Settings → 高级 → 重置本地数据(确认)。
5. 等页面 reload 完,你应该看到的是初始 sample 数据(workday/restday 那些)。
6. Settings → 同步 → 「**从快照导入**」,选刚才生成的 `.dryj` 文件,确认。
7. 页面 reload 后,应该看到你**v0.6 时代的所有真实数据**(rails、tasks 等)。
8. **关键步骤**:Settings → 同步 → **连接 Google Drive**(假设这个账号上有过测试 canonical;如果没有,先用 A profile 连一下推一份测试数据上去再继续)。
9. 弹 Modal 选「拉取云端(推荐)」。

**通过 ✅**:你 v0.6 的真实数据**没被覆盖**,而是和 Drive 里的内容**合并**显示。

**失败 ❌(CRITICAL)**:你 v0.6 的真实数据**消失了**,只剩 Drive 里的——round 6 抓的 critical bug 回归。

## 场景 5:验证「全新设备首次连接」不会污染云端

**为什么测**:这是场景 4 的反面——**没有真实数据**的全新设备,初次连 Drive 时,本地的 sample 数据**不应该**混进真实云端数据里。Round 5/6/7 反复修过这个。

**怎么测**:

1. 用 **B**(你刚创建的全新 profile,从来没装过 DayRail)。
2. 启动 v0.7。看到 sample 数据(workday/restday templates、几个示例 rail、Inbox)。
3. **不要做任何编辑**。
4. **打开 DevTools Console**,跑这条命令:
   ```js
   localStorage.getItem('dayrail.sync.samplesOnly')
   ```
   应该返回 `'1'`。如果返回 `null`,说明 boot.ts 没正确设标志,**直接报 bug**。
5. Settings → 同步 → 连接 Google Drive(用同一个账号,假设 A 已经把真实数据推上去了)。
6. 弹 Modal,选「拉取云端」。
7. 等几秒。

**通过 ✅**:
- B 上的 sample 数据**消失**,变成 A 推上去的真实数据。
- DevTools Console 里再跑一次步骤 4 的命令,应该返回 `null`(标志被清掉了)。
- 在 B 上立刻点 Settings → 同步 → 「立即同步」,提示应该是「**已是最新**」。
- 切到 A,刷新一下。**A 的数据没变**(B 没污染 A)。

**失败 ❌**:B 上同时出现 sample rails **和** A 推的数据,混在一起。或者 A 上多出 sample rails——说明污染上传了。

## 场景 6:验证 session undo 还能用

**为什么测**:v0.7 把 session undo 从 SQL 事件回滚改成了 Yjs UndoManager。Round 4 修了 sessionId origin。

**怎么测**:

1. 在 A 上打开 Cycle View(规划某个周的视图)。这个页面会自动开一个 session。
2. 做几个修改:加任务、改 rail 时间之类。
3. 点页面上的「⤺ Undo」/「Cancel」按钮(具体名字看实际 UI)。

**通过 ✅**:你 step 2 里所做的所有修改都回滚掉,回到 step 1 进入页面时的状态。

**失败 ❌**:有的修改回滚了、有的没回滚——尤其是如果你拖了任务到不同 rail(会触发 §5.5.6 的 reschedule shift),round 4 修过这种 shift 没被 session 跟踪的 bug。

## 场景 7:验证 backup history 「恢复」按钮(可选)

**为什么测**:Round 3 修了一次没修对,round 4 改用 `applyImportedUpdate` 才修对——「从备份历史恢复」之前会数据消失。

**怎么测**:

1. A 用了一段时间,Drive 上累积了一些 history(可以在 Settings → 同步 → 备份历史 看到列表)。
2. 找一个**几天前**的历史快照,点「恢复」。
3. 弹窗确认。

**通过 ✅**:那份历史快照里的内容合并到当前本地(不是覆盖)。等大约 60 秒,再看 Settings 的 lastSync 时间应该刷新——说明已经 push 上 Drive 了。

**失败 ❌**:历史快照内容不出现;或者出现了但 60 秒后 lastSync 没刷新(说明没 push,数据被困在本地了)。

## 场景 8:验证慢网启动不污染(可选,有点麻烦)

**为什么测**:Round 7 抓的 RuntimeSyncDialog 边角 case——慢网启动时 boot peek 超时,seed 跑了,然后网络恢复后周期性 probe 触发,有可能把 sample 数据合到云端。

**怎么测**:

1. DevTools → Network 标签 → 把 throttling 设成「Slow 3G」。
2. 重置本地数据(Settings → 高级 → 重置)。
3. 重启 page。会很慢,可能要 10-20 秒。
4. 启动后看到 sample 数据。
5. **不要编辑**。
6. 把网络改回「No throttling」。
7. 等 30 秒(让 visibility/online probe 触发)。

**通过 ✅**:本地 sample 消失,变成云端真实数据。云端没有被污染。

**失败 ❌**:本地保留 sample,然后跟云端真实数据混在一起出现。

## 场景 9:.dryj 损坏后能恢复(可选,纯防御性)

**为什么测**:验证如果硬盘上的 .dryj 文件损坏了,app 不会卡死,而是给你恢复路径。

**怎么测**:

1. DevTools Console:
   ```js
   const root = await navigator.storage.getDirectory();
   const f = await root.getFileHandle('dayrail-state.dryj', { create: true });
   const w = await f.createWritable();
   await w.write(new Uint8Array([0xff, 0xff, 0xff]));
   await w.close();
   ```
2. F5 刷新页面。

**通过 ✅**:出现 BootError 页面,提示「OPFS 里的 .dryj 损坏」,有「清空本地数据并重新启动」按钮。点它能恢复(连了 Drive 的话从 Drive 拉回数据)。

**失败 ❌**:白屏、卡死、或者 console 一堆错没有 UI 提示。

## 场景 10:平常用一用看看有没有奇怪现象(必跑)

**为什么测**:有些 bug 只有在真实使用模式下才会冒出来,清单覆盖不到。这一步就是「随便用 5 分钟」。

**怎么测**:就用就好了。建议覆盖以下操作:
- 创建/编辑/删除任务,改优先级、改状态、加 subitem。
- 用 schedule(把任务排到某个 rail / 某个时段)。
- 写一段 daily reflection。
- 创建一个 habit binding(如果你用 habit 功能)。
- 编辑一个 calendar rule。
- 创建一个 line(项目/习惯/标签),再删掉。

每一步做完都刷新一下页面,看数据是否还在。每隔几分钟看一眼 Settings → 同步,看 lastSync 时间有没有更新。

**通过 ✅**:所有操作即时显示且刷新后还在,Drive sync 不会卡 error,顶栏不会一直显示同步中或离线。

**失败 ❌**:任何「我刚做的事情没保存」「同步状态卡住」「翻到某个页面突然空了」。

## 已知保留行为(不是 bug,别担心)

- **Daily reflections 在 v0.6 → v0.7 迁移后是空的**:v0.6 的 JSON 导出本来就不带 reflections(它原本是本地数据)。迁移脚本会在跑的时候打印警告。
- **同字段不同新值的真冲突静默挑一边**:v0.7 的 CRDT 在「两台设备同时改同一字段成不同值」时,用 Lamport 时钟选一边赢,**不弹 UI**。这种场景在单用户多设备里极少;如果你**频繁**遇到「我改的被无声覆盖了」,告诉我。
- **顶栏可能短暂显示「同步中」一下又消失**:周期性 probe 偶尔触发,正常。
- **Drive 的 history 列表里偶尔多出来一份「时间挨得很近」的快照**:round 5/6 的 timer 残留留下的;不会丢数据,只是多占一个 history slot。我已经修了主要路径,但极端情况可能还有。
